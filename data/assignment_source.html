01The problem

Teams that work with engineering and technical documents — drawings, specs, plan sets, P&IDs — constantly deal with revisions. Rev B replaces Rev A; a scanned as-built supersedes a drawing; a redlined markup goes back to the CAD file. The recurring, expensive question is always the same: “what actually changed between these two, and does it matter?”

Today that comparison is manual, slow, and error-prone. Someone flips between two documents, eyeballs the differences, and hopes they didn't miss a changed dimension, a deleted note, a moved valve, or a revised tolerance.

Your task is to build the core of a tool that automates this. Given two PIDs (each a reference to a document revision), the system should ingest both regardless of format, compute a structured delta, produce a human-readable delta report, and expose a chat interface grounded in the two documents and the delta so a user can ask questions like “what changed on sheet 3?” or “did any dimensions change near the pump?” and get a cited, trustworthy answer.

Why this assignment. It is deliberately open-ended and mirrors real Applied AI work: messy multi-format inputs, a retrieval/reasoning layer, an LLM you don't fully control, and a hard requirement that the result be observable and measurable. We care far more about your judgment, trade-offs, and evaluation rigor than about a pixel-perfect UI.

02Domain language

Use this vocabulary consistently in your code, comments, and report. It is the shared language of the domain and of this assignment.

TermMeaning in this assignment
PIDThe persistent identifier for a single document/drawing revision in the system. You are given two PIDs that reference two revisions of the same underlying document. Treat a PID as the handle you resolve to raw bytes + metadata (format, page/sheet count, revision label). (Not to be confused with a P&ID — see below — though the two often coincide in this domain.)
DeltaThe set of meaningful changes from PID A (base) to PID B (revised): additions, deletions, and modifications. A delta is structured (typed, located, described) — not just a raw pixel or text diff.
Delta reportThe human-readable, machine-parseable artifact summarizing the delta: what changed, where (page/sheet/region), change type, and a confidence signal. This report is itself a retrievable source for chat.
Markup bonusA visual overlay that draws the delta back onto the document (e.g., boxes/highlights on the changed regions, redline-style annotations). The classic manual artifact this tool replaces.
Native PDFA PDF with an extractable text/vector layer (born-digital). Text, coordinates, and often tables can be read directly.
Scanned PDFA raster/image PDF with no reliable text layer — a photo or scan. Requires OCR and/or vision to recover content and layout.
DWGA native CAD drawing file (AutoCAD). Vector geometry, layers, blocks, text entities, and dimensions. Rich structure, but a binary format that needs a parser/converter.
P&IDPiping & Instrumentation Diagram — a common document type in this space. Mentioned so the PID abbreviation is unambiguous: in this assignment PID = document identifier, not the diagram type.
OCROptical Character Recognition — recovering text (and ideally bounding boxes) from a raster page.
Canonical representationThe format-agnostic intermediate model your pipeline normalizes every input into, so the delta engine and chat layer never care whether the source was PDF, scan, or DWG. Designing this well is the crux of the assignment.
GroundingEnsuring every chat answer is traceable to specific source content (a PID + location, or a delta-report entry) rather than model imagination. Answers should carry citations.
Retrieval (RAG)Selecting the relevant slices of the two PIDs and the delta report to condition the LLM on, at query time.
Ground truthHuman-labeled “correct” deltas / answers for a handful of document pairs, used by your eval harness to score the system.
TraceThe end-to-end record of one request (ingest → delta → retrieve → LLM → answer) with timings, token/cost, inputs, and outputs, for observability.

03What you'll build

Five capabilities. The pipeline, delta, report, and chat are core. Observability and eval are required. Markup is a bonus.

A. Format-agnostic ingestion core

Resolve a PID to bytes, detect the format, and normalize it into your canonical representation. Design an abstraction where new formats plug in behind one interface. You must demonstrate at least two of the three formats working end-to-end (native PDF + one of scanned PDF / DWG). The third may be stubbed but the seam must be real, not hypothetical.

B. Delta engine core

Given two canonical documents, compute a structured delta: added / removed / modified items, each with a type (text, dimension, note, geometry, table cell…), a location (page/sheet + region), a description, and a confidence. Be explicit about how you align content between revisions — matching is the hard part, not diffing.

C. Delta report core

Render the delta as a report that is both human-readable and machine-parseable (e.g., Markdown/HTML + JSON). It should summarize counts, group changes sensibly, and be a first-class retrievable source for chat.

D. Grounded chat core

A chat interface (CLI, API, or minimal web UI — your call) that answers questions over both PIDs and the delta report. Answers must be grounded with citations back to a PID + location or a delta entry. Handle “what changed?” style questions and content questions about either revision.

E. Delta markup bonus

Overlay the computed delta visually on the document — bounding boxes / highlights / redline annotations on the changed regions, exported as an annotated PDF or image. Strong signal if you get even a partial version working, but do not sacrifice A–D for it.

04Technical requirements & constraints

  • Language / stack: your choice. Python is expected for the AI/ML core but not mandatory.
  • LLM: any provider or model (hosted or local). Keep it swappable behind an interface and read credentials from env vars. Never commit keys.
  • Determinism: the delta engine's structural output should be reproducible; isolate LLM non-determinism and document where it lives.
  • Config over hardcoding: model, thresholds, and paths configurable.
  • Reproducible run: a single documented command (or docker compose up) that ingests a provided pair and produces a delta report + lets us chat.
  • Sample data: include at least 2–3 document pairs you used (or synthesize them — e.g., edit a PDF and re-export, scan/photograph a printout, tweak a DWG). Document their provenance.
  • No key or PII committed to the repo.
Depth over breadth. A narrow system that ingests two formats, computes a genuinely useful delta, chats with citations, and is well-instrumented and well-evaluated beats a sprawling one that does everything shallowly. Cut scope deliberately and write down what you cut and why.

05Observability required

The repo must ship with real observability — not just print statements. We want to open your project and see what the system did on a given request.

  • Tracing: each request produces a trace spanning ingest → delta → retrieval → LLM call → answer, with per-stage timing.
  • LLM telemetry: capture prompts, responses, model name, token counts, and estimated cost per call.
  • Structured logging: JSON logs with a correlation/request id, not free-text.
  • Metrics: latency, token/cost, delta counts, retrieval hit stats — surfaced somewhere inspectable (a dashboard, a served metrics endpoint, or at minimum a written trace file per run).
  • Failure visibility: errors (bad OCR, unparseable DWG, LLM timeout) are captured and traceable, not swallowed.

Any tooling is fine — OpenTelemetry, Langfuse/Phoenix/LangSmith, Prometheus + Grafana, or a well-designed homegrown tracer. Justify your choice in the README.

06Evaluation harness required

An evaluation harness must live in the repo and be runnable. This is where an Applied AI Engineer is judged most sharply: can you tell whether your system is actually good, and prove it changed for the better or worse?

  • Eval dataset: a small labeled set — document pairs with expected deltas, plus Q&A pairs over them (ground truth).
  • Delta metrics: precision / recall / F1 on detected changes (did you find the real changes, and avoid inventing fake ones?).
  • Chat metrics: answer correctness and groundedness / citation accuracy (LLM-as-judge is acceptable if you validate the judge).
  • Runnable command: make eval (or equivalent) prints a scorecard.
  • Regression-friendly: results are comparable across runs so a change can be shown to help or hurt.
  • Honesty: report where the system fails. A candid failure table is a strong positive signal.

  • Ingests ≥2 of 3 formats behind one adapter interface.
  • Produces a structured delta (typed, located, confidence) for a provided pair.
  • Emits a delta report that is human- and machine-readable.
  • Chat answers questions over both PIDs + the delta, with citations.

  • Per-request traces with stage timings + LLM token/cost.
  • Structured logs with a correlation id.
  • Eval harness runnable via one command, prints a scorecard.
  • Delta + chat metrics reported, including at least one failure case.
  • No secrets committed; .env.example present.

bonus Working (even partial) delta markup overlay · all three formats · a small served UI/dashboard · thoughtful retrieval evaluation · cost/latency budget analysis.

11FAQ & constraints

Does “PID” mean a P&ID diagram?

No — here PID is a document identifier. You are handed two PIDs (two revisions). The documents may happen to be P&IDs, engineering drawings, or plan sheets, but treat a PID purely as a resolvable reference to one revision's bytes + metadata.

Which two formats should I prioritize?

Native PDF + scanned PDF is the pragmatic pair (OCR shows off Applied AI judgment). DWG is the most impressive if you can parse or convert it, but it's fine to keep DWG as a real stub behind the adapter seam.

How “smart” must the delta be?

Smarter than a raw text/pixel diff. We want change alignment and classification with locations and confidence. You choose how much LLM vs. deterministic logic to use — and justify it.

Can I use frameworks (LangChain, LlamaIndex, etc.)?

Yes, any. We care that you understand what they do under the hood and can instrument and evaluate them.

What if I can't find real DWG/scanned samples?

Synthesize them: export a PDF twice with edits, print-and-scan (or photograph) a page, or edit a sample DWG. Document provenance in data/samples/.
